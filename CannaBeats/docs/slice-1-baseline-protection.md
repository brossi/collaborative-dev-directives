## Player or operator outcome

CannaBeats can be restored and rolled back without reconstructing accounts, authorization, catalog, deployment, or managed-source configuration from memory. When a problem occurs, an operator can identify the affected component and give a family tester a safe correlation reference without manually reading SQLite or joining unrelated free-form log lines.

The first delivery gate combines recoverability with a thin observability foundation. Later slices should not introduce schema-heavy or operationally risky changes until a known-good release can be restored and failures from that release can be distinguished.

## Included backlog items

- Encrypted application-data backup, retention, and a restore rehearsal
- Application and database-migration rollback isolated from unrelated `vw-services` workloads
- Known-good application and catalog version recording
- Catalog validation and rollback protections
- Managed audio-source replacement and Spotify reauthorization procedure
- Health and capacity checks for the application, database volume, relay, certificates, and managed source
- Structured, redacted operational errors with correlation identifiers
- An authorized, read-only current/recent session summary
- Secret inventory and verification that diagnostics do not disclose secrets

## Explicitly excluded

- A hosted log aggregation or general monitoring platform
- Distributed tracing infrastructure or vendor-specific telemetry SDKs
- Durable event sourcing or retention of every request
- Stable client action identifiers and idempotent game commands
- The Slice 2 significant-game-event and managed-audio lifecycle ledger
- Per-listener audio timing, buffer, underrun, or device profiling
- Persistent player statistics, analytics dashboards, or cross-session profiles
- Backing up or imaging the managed source's Spotify browser profile

## Current-state evidence

- The access service health route executes `SELECT 1`, while the game service health route only confirms that its process can answer. Neither produces one component view of the game service, shared database, relay, and managed source.
- Docker health checks and bounded `json-file` rotation already exist for the access and game containers. They are useful deployment primitives, but the services emit mostly free-form output and do not share an event schema or correlation identifier.
- The access service logs unexpected server errors with `console.error(method, path, error)` and returns a generic message. The game API has route-local response helpers. A tester cannot supply a safe reference that connects a response to the relevant server output.
- SQLite already contains lobby/run snapshots, account and guest last-seen times, managed-source heartbeats, leases, playback status, and transient command outcomes. These facts can support a conservative read-only summary without first creating an analytics schema.
- A lobby snapshot's `playing` status and polling-derived last-seen fields do not prove that people are actively playing. Before Slice 2 adds durable significant events, the summary must label liveness as confirmed, inferred, stale, or unavailable.
- The repository contains PoC deployment configuration, but the durable environment, sibling `vw-services` deployment boundary, backup destination, certificate checks, and source-droplet provisioning must be inventoried against the running environment before their runbooks are finalized.

## Dependencies and contracts

### Thin observability contract

#### Structured operational records

Services emit one JSON object per operational record to standard output or standard error. The initial common fields are:

| Field | Requirement |
| --- | --- |
| `timestamp` | UTC ISO-8601 timestamp generated by the service |
| `level` | `debug`, `info`, `warn`, or `error` |
| `service` | Stable service name such as `access` or `game` |
| `environment` | A low-cardinality name such as `development`, `poc`, or `family` |
| `event` | Stable machine-readable event or error code |
| `message` | Short human-readable text containing no secret or pre-reveal data |
| `correlationId` | Present for request work and propagated internal work |
| `method`, `route`, `status`, `durationMs` | Optional safe HTTP context; `route` is a template or path without a query string |
| `lobbyId`, `runId`, `sourceId`, `leaseId` | Optional internal identifiers when they materially aid diagnosis |
| `errorType` | Optional stable exception or failure category, not an unsanitized provider payload |
| `applicationVersion`, `catalogVersion` | Running versions when known |

High-frequency polling success is not logged per request at `info`. The foundation records startup/shutdown, configuration validation, readiness transitions, unexpected failures, security-relevant rejections where useful, and significant dependency-state changes. Sampling or lower severity may be used for repetitive expected failures.

#### Correlation behavior

- The public application boundary generates an opaque correlation identifier for every request. It does not trust a caller-supplied value as authority or identity.
- Trusted internal calls propagate the correlation identifier in one documented HTTP header. Each service validates its syntax and generates a replacement when it is absent or malformed.
- Every HTTP response returns the correlation header. Error responses also include a stable, user-safe error code and the correlation reference without exposing internal details.
- Correlation identifiers grant no access and are never accepted in place of authentication, lobby membership, an invitation, or a game action identifier.
- Slice 2 action identifiers remain distinct: an action ID establishes idempotency for a user intent, while a correlation ID connects operational evidence produced while handling it.

#### Redaction and safe context

Central helpers enforce an allowlist of structured fields. Tests use sentinel secrets and fail if any appear in an emitted record or error response.

Never emit:

- `Authorization` or `Cookie` values, session tokens, secret-file contents, signing keys, passkey material, or Spotify credentials
- Invitation, download, handoff, pairing, or authorization capabilities, whether plain or hashed
- Full request bodies, raw query strings, or unreviewed upstream/provider response bodies
- Private browser or Spotify device identifiers
- Pre-reveal title, artist, year, artwork, track URI, or other answer-bearing metadata
- Display names or other personal fields when an internal identifier or count answers the operational question

Expected client errors use stable categories and safe messages. Unexpected errors retain a sanitized error type and operator-useful context; stack capture, if retained in short-lived local logs, must pass the same redaction tests and never be returned to a client.

#### Health and readiness

Health has three different audiences and must not collapse them:

1. **Public liveness:** a minimal, unauthenticated response proving that the process can answer. It exposes no topology, identifiers, capacity, or secret/configuration detail.
2. **Deployment readiness:** confirms that the service can safely receive its normal traffic, including required configuration, catalog/version availability, and a bounded database check. A managed source that is optional for local playback does not make the game service unready.
3. **Authorized component diagnostics:** reports `healthy`, `degraded`, `unavailable`, or `unknown` for the access service, game service, database/volume, relay, managed source, and certificate checks, with checked-at time and a safe reason code.

Component checks have explicit timeouts and cannot block ordinary requests indefinitely. A dependency failure produces a state transition record rather than a log line on every health poll.

#### Read-only operator summary

The first operator surface is a command-line report or equivalent internal command. It reads existing data without modifying session state, renewing a lease, consuming a command, updating last-seen timestamps, or exposing a public administration endpoint.

For each current or recent lobby it reports, where known:

- Safe lobby and active-run identifiers, creation/update times, phase, and round
- Participant/seat counts and control types; names are excluded by default
- Last meaningful state-change time available from the current snapshot
- Safe client-presence facts and their timestamps
- Managed-source online/lease/playback state and lease expiry
- Recent known error category from existing source/lease/command state
- `active`, `idle`, `stale`, `completed`, `abandoned`, or `unknown`, together with the facts used and any missing history
- Running application/catalog version and component-health summary

The Slice 1 command does not claim chronological reconstruction. When existing snapshots cannot prove the last action, abandonment, playback acknowledgement, or recovery, it says `unknown` or `history unavailable`. Slice 2 replaces those gaps with selected durable events.

#### Storage and retention boundary

- Operational records remain in bounded container output with documented rotation and operator access. The existing local `json-file` limit may be retained if the environment audit confirms it is sufficient.
- No new remote log sink is required for Slice 1.
- Health responses are current observations, not history.
- The operator summary reads current/recent operational state; it does not turn logs into the system of record.
- Only version/deployment metadata required for rollback is durable in this slice. Significant game and audio outcomes receive a separate schema and retention decision in Slice 2.

### Recovery contracts

- The backup identifies the exact database and operational configuration included, encryption method, destination, retention, restore prerequisites, and items intentionally excluded.
- A restore targets a clean test location first and never overwrites the live database during rehearsal.
- Rollback identifies application image/version, catalog version, schema compatibility, and the exact CannaBeats services affected.
- Health/readiness and a short smoke test verify restore and rollback success.
- The deployment procedure does not restart, replace, or migrate unrelated `vw-services` workloads.

## Data or migration impact

The thin observability foundation should not require a gameplay-event migration. Prefer process/release metadata supplied by the build or deployment and read-only queries over existing tables.

If durable deployment/catalog version metadata cannot be recorded outside the application database, add only a small backward-compatible operational metadata table. Any database change must be covered by backup, restore, forward migration, and rollback compatibility before deployment.

## Failure and recovery behavior

- A logging failure cannot prevent a game request from completing; the helper falls back to a minimal safe standard-error record.
- A malformed or missing correlation value is replaced, never echoed blindly.
- A dependency timeout produces `degraded`, `unavailable`, or `unknown` without leaking connection details.
- Managed-source or relay failure does not make local gameplay falsely fail liveness/readiness when local audio remains a valid mode.
- An operator-report query failure exits nonzero, prints a correlation reference and safe error, and performs no partial cleanup or repair.
- Restore and rollback procedures stop on failed integrity, migration, version, or health checks and retain the previous recoverable state.

## Acceptance criteria

### Recoverability

- An encrypted backup restores the intended accounts, capabilities, device authorizations, lobby/run state, and operational configuration into a clean test location.
- The restore rehearsal records duration, verification results, omissions, and the exact recovery point.
- A failed application/catalog deployment can return to a named known-good version without disturbing unrelated services.
- Managed-source loss can be recovered using a documented replacement and Spotify reauthorization procedure without copying its browser profile.

### Thin observability

- A request crossing the public boundary and at least one internal service produces structured records carrying the same correlation identifier, and the response exposes that reference safely.
- Expected and unexpected failure tests prove that credentials, cookies, capability values, device identifiers, request bodies, query strings, provider payloads, and pre-reveal metadata do not appear in logs or responses.
- Public liveness, deployment readiness, and authorized component diagnostics have distinct tests and failure semantics.
- The operator can distinguish application, database, relay, and managed-source failure or explicitly see that a component is `unknown`.
- The operator summary answers what current/recent sessions exist and what is known about their progress, presence, lease, and errors without changing any row.
- The summary distinguishes confirmed facts, conservative inference, and unavailable history; it never treats a stale `playing` flag or polling tab as proof of active play.
- Container-log rotation and access are documented, and emitted records include the running application and catalog versions when available.
- The implementation adds no hosted observability dependency and no per-listener or per-frame telemetry.

## Verification plan

- Unit-test correlation generation/validation, propagation, error envelopes, structured serialization, and redaction with sentinel secret values.
- Integration-test a public request through access and game services and assert one shared correlation reference in responses and captured output.
- Inject database, relay, managed-source, and configuration failures and assert their independent health/readiness states and safe reason codes.
- Run the operator summary against fixtures for lobby-only, active run, stale run, completed run, expired lease, offline source, and missing-history cases; compare the database before and after byte-for-byte or by a no-write connection check.
- Exercise log-volume behavior under normal polling to confirm successful polls do not flood bounded storage.
- Perform backup/restore and deployment/catalog rollback rehearsals in a disposable target and record their evidence in the runbook.
- Run the existing access, game API, security, catalog, and tooling suites before deployment.

## Adversarial-audit P2 remediation plan

Commit `f3bfc94` is the clean P1 checkpoint. The remaining P2 findings are part of
Slice 1 unless explicitly assigned to Slice 2 below. They will be implemented as
five independently reviewable, test-first increments in dependency order.

### P2-A: Backup integrity and scale

Status: implemented and locally verified on 2026-08-11; real-container and
off-host rehearsal remains in P2-E.

Implement first because every release and migration safeguard depends on a
trustworthy recovery artifact.

- Exercise the SQLite online backup while a WAL-mode writer remains open and
  commits during the backup.
- Stream snapshot encryption and decryption without buffering or base64-encoding
  the complete database, and keep working data off the bounded container tmpfs.
- Publish a completed backup atomically only after its contents are flushed; a
  failed create leaves neither a final artifact nor a misleading partial backup.
- Authenticate every recognized retention candidate before deleting any older
  artifact; one corrupt or foreign candidate stops the entire prune operation.
- Preserve verification and restore support for the version-1 envelope so
  existing recovery artifacts do not become unreadable.

Gate: concurrent-write, interrupted-publication, corrupt-retention, large-file,
legacy-format, verify, and restore tests pass. The runbook describes the new
format and atomic publication behavior.

### P2-B: Transactional release and migration safety

Status: implemented and locally verified on 2026-08-11; real Docker failure and
rollback rehearsal remains in P2-E.

Implement after P2-A so migration and interruption tests have a dependable
recovery point.

- Define the supported SQLite `user_version` range for each application release
  and reject a forward deploy or rollback that cannot read the target database.
- Serialize release and rollback operations with a host lock.
- Replace release records atomically and make interruption at build, start,
  readiness, record promotion, and rollback recover to an unambiguous state.
- Keep application/catalog identity and exact image IDs consistent across all
  current, previous, and bootstrap records.

Gate: compatibility-matrix, concurrent-release, and transition fault-injection
tests pass before another schema-bearing release is attempted.

### P2-C: Truthful component health and managed-source recovery

Implement after release safety because the resulting checks become deployment
and rollback evidence.

- Validate the component being reported instead of treating a process response
  or source heartbeat alone as health.
- Include known source errors, configuration validity, authentication readiness,
  capacity, and bounded dependency timeouts in safe component states.
- Make managed-source provisioning reproducible, including the VNC password-file
  installation contract and Spotify reauthorization prerequisites.
- Preserve `unknown` when a check cannot establish a fact.

Gate: injected access, database/volume, relay, certificate, managed-source,
configuration, and timeout failures produce the documented independent states.

### P2-D: Observability and scheduler completion

Implement after health semantics stabilize so logging records meaningful state
transitions rather than an interim component model.

- Suppress successful polling and repeated dependency-failure floods while
  emitting startup, shutdown, readiness, and dependency state transitions.
- Close remaining error-envelope inconsistencies and enforce the game logger's
  structured-field allowlist with sentinel redaction tests.
- Give scheduled backup and operational checks explicit timeouts and an
  actionable local failure-notification path.

Gate: log-volume, transition, error-envelope, redaction, timeout, and scheduler
failure tests pass without adding a hosted observability dependency.

### P2-E: Real-environment rehearsal and closure

Perform after P2-A through P2-D, with an early Compose validation as soon as a
Docker runtime is available.

- Validate the production and isolated-restore Compose definitions using the
  host's Docker Compose version and non-secret environment.
- Create a real encrypted off-host backup, restore it into the isolated target,
  and record duration, size, recovery point, integrity, and row-count evidence.
- Inject a failed deployment and demonstrate exact-image and schema-compatible
  rollback without restarting unrelated workloads.
- Exercise the real relay, certificate, database-volume, and managed-source
  diagnostics and record capacity observations.
- Update the runbook and rehearsal record with measured results and remaining
  environmental limitations.

Gate: all Slice 1 acceptance criteria have recorded evidence. Full Xcode is not
required for these gates; a real Docker/host environment is required.

### Deferred to Slice 2

Stable action identifiers, durable significant-game and managed-audio event
history, per-listener audio profiling, and richer chronological reconstruction
remain Slice 2 work. P2 remediation must not pull those schemas or telemetry into
the thin Slice 1 foundation.

## Deployment and rollback plan

Implement Slice 1 in three checkpoints:

1. **Recovery inventory and rehearsal:** identify durable data/configuration, create the encrypted backup, restore it in a clean target, and document the current independent rollback boundary.
2. **Thin observability foundation:** deploy structured/redacted errors, correlation, distinct health/readiness checks, version identity, and the read-only operator summary. Re-run restore and rollback smoke checks with the new diagnostics available.
3. **Protection completion:** add remaining component/capacity checks, catalog release gates, known-good catalog rollback, and the managed-source replacement/reauthorization runbook.

Each checkpoint is independently testable and revertible. Application changes roll back to the prior image/version. Additive operational metadata, if introduced, remains readable or safely ignored by the prior release. A rollback never deletes the new backup, rehearsal evidence, or prior known-good artifacts.
